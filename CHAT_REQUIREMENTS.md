# Технические требования к системе чата

## 1. Общая информация

### 1.1. Назначение
Система общения между сотрудниками организации для обмена сообщениями, файлами и фотографиями.

### 1.2. Целевая аудитория
- Количество пользователей: ~350 человек
- Одновременная активность: не все пользователи одновременно
- Требования к доступности: круглосуточно

### 1.3. Основные требования
- Личные чаты (обязательно)
- Групповые чаты
- Передача файлов и фотографий
- История сообщений
- Отметки о прочтении
- Поиск по сообщениям
- Простой интерфейс создания чата (как в Битрикс24)

### 1.4. Ключевые особенности интерфейса (как в Битрикс24)
- **Личный чат**: Пользователь выбирает сотрудника из списка → чат открывается сразу (создается автоматически при первом сообщении)
- **Групповой чат**: Кнопка "Создать группу" → выбор участников → ввод названия → создание
- **Переводы**: Только для интерфейса (кнопки, меню). Сообщения пользователей не переводятся - пишут на любом языке
- **Название группы**: Только для групповых чатов, указывается пользователем на любом языке
- **Описание группы**: Не требуется

## 2. Функциональные требования

### 2.1. Чаты (Conversations)

#### 2.1.1. Типы чатов
- **Личный чат** - обязательный тип, основной способ общения
- **Групповой чат** - для общения нескольких участников

#### 2.1.2. Создание чата

##### Личный чат
- Пользователь выбирает сотрудника из списка
- Чат создается автоматически при первом сообщении
- Название чата формируется автоматически из имени собеседника
- Если чат уже существует, открывается существующий

##### Групповой чат
- Пользователь нажимает кнопку "Создать группу"
- Выбирает участников из списка сотрудников (можно несколько)
- Указывает название группы (обязательно, только на русском языке)
- Описание группы не требуется
- Чат создается сразу после выбора участников и указания названия

##### Интерфейс создания
- Список всех сотрудников с возможностью поиска
- Для личного чата: клик по сотруднику → сразу открывается чат
- Для группового: кнопка "Создать группу" → выбор участников → ввод названия → создание

#### 2.1.3. Управление чатом
- Добавление участников (только для групповых чатов)
- Удаление участников (только для групповых чатов, создатель/администратор)
- Изменение названия группы (только для групповых чатов, создатель/администратор)
- Архивация чата
- Роли участников (только для групповых чатов):
  - Участник (member) - обычный пользователь
  - Администратор (admin) - создатель группы, полный контроль

### 2.2. Сообщения (Messages)

#### 2.2.1. Отправка сообщений
- Текстовые сообщения (без ограничений по языку - пользователи пишут как хотят)
- Сообщения с вложениями (файлы, фото)
- Ответ на сообщение (reply) 
- Редактирование своих сообщений
- Удаление своих сообщений

**Важно**: Переводы применяются только к интерфейсу (кнопки, меню, заголовки). 
Содержимое сообщений не переводится - пользователи пишут на любом языке.

#### 2.2.2. Ограничения
- Максимальная длина текста: 5000 символов
- Максимальный размер файла: 20 МБ
- Разрешенные типы файлов:
  - Изображения: JPG, PNG, GIF, WEBP
  - Документы: PDF, DOC, DOCX, XLS, XLSX
  - Архивы: ZIP, RAR

#### 2.2.3. История сообщений
- Хранение всей истории сообщений
- Пагинация при загрузке (50-100 сообщений на страницу)
- Загрузка старых сообщений по требованию
- Поиск по истории сообщений

### 2.3. Вложения (Attachments)

#### 2.3.1. Типы вложений
- Изображения (image) - с автоматическим созданием миниатюр
- Документы (document)
- Видео (video) 
- Аудио (audio)
- Другое (other)

#### 2.3.2. Обработка изображений
- Автоматическое создание миниатюр для превью
- Сохранение оригинального файла (в зависимости от стратегии хранения)
- Оптимизация размера (опционально)

#### 2.3.3. Стратегия хранения файлов

**Основная стратегия: Временное хранение с автоудалением**

**Проблема**: Хранение всех файлов на сервере может привести к нехватке места на диске Docker контейнера.

**Решение**: 
- Файлы хранятся на сервере временно
- Автоматическое удаление файлов старше определенного периода (по умолчанию 30-90 дней, настраивается)
- Файлы доступны только пока не удалены
- Минимальное использование дискового пространства

**Преимущества**:
- ✅ Простая реализация, не требует внешних сервисов
- ✅ Контролируемое использование дискового пространства
- ✅ Настраиваемый период хранения
- ✅ Можно реализовать сразу при разработке

**Недостатки**:
- ⚠️ Файлы могут быть удалены, если не скачаны вовремя (но период хранения достаточный)
- ⚠️ Требуется задача для автоматического удаления (простая Django management command)

**Реализация**:
- Django management command для удаления старых файлов
- Настройка периода хранения в `settings.py` (например, `MESSAGING_FILE_RETENTION_DAYS = 30`)
- Запуск команды через cron или Celery периодические задачи

**Альтернативы (для будущего)**:
- Внешнее облачное хранилище (S3, Yandex Object Storage) - если потребуется неограниченное хранилище
- Можно добавить позже без изменения основной логики

### 2.4. Отметки о прочтении

#### 2.4.1. Функционал
- Автоматическая отметка при открытии чата
- Отображение количества непрочитанных сообщений
- Индикатор "прочитано" для каждого сообщения
- Время последнего прочтения

### 2.5. Уведомления

#### 2.5.1. Типы уведомлений
- Новое сообщение в чате
- Упоминание пользователя 
- Новый участник в чате

#### 2.5.2. Настройки
- Включение/выключение уведомлений для каждого чата

## 3. Технические требования

### 3.1. Архитектура

#### 3.1.1. Backend
- **Фреймворк**: Django 5.2+
- **API**: Django REST Framework
- **База данных**: PostgreSQL
- **Подход**: REST API + Long Polling
- **Аутентификация**: Django Session Authentication

#### 3.1.2. Frontend
- **Фреймворк**: Alpine.js 3.x
- **HTTP клиент**: Fetch API
- **Стили**: Tailwind CSS (уже используется в проекте)
- **Иконки**: Font Awesome (уже используется)
- **Механизм обновления**: Long Polling (каждые 3-5 секунд)

### 3.2. Структура приложения

```
messaging/
├── models.py          # Модели: Conversation, Message, Attachment, Participant
├── views.py           # REST API views
├── serializers.py     # DRF сериализаторы
├── urls.py            # API маршруты
├── admin.py           # Админка для модерации
├── permissions.py     # Права доступа
└── utils.py           # Утилиты (обработка файлов и т.д.)
```

### 3.3. Модели данных

#### 3.3.1. Conversation (Чат)
- `type` - тип чата (direct/group)
- `name` - название чата (только для групповых чатов, на русском языке)
  - Для личных чатов: название формируется автоматически из имени собеседника
  - Для групповых: название указывает пользователь при создании
- `created_by` - создатель
- `is_archived` - архивирован ли
- `created_at`, `updated_at` - временные метки

**Примечание**: Описание чата не требуется. Связь с департаментом/управлением не нужна.

#### 3.3.2. ConversationParticipant (Участник)
- `conversation` - чат
- `user` - пользователь
- `role` - роль (member/admin)
  - Для личных чатов: всегда member
  - Для групповых: admin - создатель группы, member - остальные участники
- `last_read_at` - время последнего прочтения
- `notifications_enabled` - уведомления включены
- `joined_at`, `left_at` - временные метки

#### 3.3.3. Message (Сообщение)
- `conversation` - чат
- `sender` - отправитель
- `text` - текст сообщения
- `is_edited` - отредактировано ли
- `is_deleted` - удалено ли
- `reply_to` - ответ на сообщение
- `created_at`, `updated_at`, `deleted_at` - временные метки

#### 3.3.4. MessageAttachment (Вложение)
- `message` - сообщение
- `file` - файл (путь к файлу на сервере или URL для внешнего хранилища)
- `filename` - оригинальное имя файла
- `file_type` - тип файла
- `file_size` - размер файла
- `thumbnail` - миниатюра (для изображений)
- `storage_type` - тип хранения (local/temporary/external) - опционально, по умолчанию temporary
- `expires_at` - дата истечения срока хранения (для временных файлов) - опционально
- `created_at` - временная метка

**Примечание**: Для экономии места на диске рекомендуется использовать временное хранение с автоудалением.

#### 3.3.5. MessageRead (Прочтение)
- `message` - сообщение
- `user` - пользователь
- `read_at` - время прочтения

### 3.4. API Endpoints

#### 3.4.1. Чаты
```
GET    /api/messaging/conversations/                    # Список чатов пользователя
POST   /api/messaging/conversations/                    # Создать групповой чат
GET    /api/messaging/conversations/{id}/               # Детали чата
PUT    /api/messaging/conversations/{id}/               # Обновить чат (название группы)
DELETE /api/messaging/conversations/{id}/               # Удалить/архивировать чат
GET    /api/messaging/conversations/direct/{user_id}/   # Получить или создать личный чат с пользователем
```

#### 3.4.1.1. Сотрудники
```
GET    /api/messaging/contacts/                         # Список всех сотрудников для выбора

```

#### 3.4.2. Сообщения
```
GET    /api/messaging/conversations/{id}/messages/     # Получить сообщения
POST   /api/messaging/conversations/{id}/messages/     # Отправить сообщение
PUT    /api/messaging/messages/{id}/                   # Редактировать сообщение
DELETE /api/messaging/messages/{id}/                   # Удалить сообщение
```

#### 3.4.3. Участники
```
GET    /api/messaging/conversations/{id}/participants/        # Список участников
POST   /api/messaging/conversations/{id}/participants/        # Добавить участника
DELETE /api/messaging/conversations/{id}/participants/{user_id}/  # Удалить участника
```

#### 3.4.4. Прочтение
```
GET    /api/messaging/conversations/{id}/unread/       # Количество непрочитанных
POST   /api/messaging/messages/{id}/read/             # Отметить как прочитанное
```

#### 3.4.5. Поиск
```
GET    /api/messaging/search/?q=...&conversation_id=...  # Поиск по сообщениям
```

## 6. Интеграция с существующей системой

### 6.1. Связь с моделями

#### 6.1.1. Связь User ↔ Contact (Опциональная OneToOne)

**Архитектура**: Опциональная связь `OneToOneField` между `User` и `Contact`

**Реализация**:
```python
# В модели Contact добавить поле:
user = models.OneToOneField(
    User,
    on_delete=models.SET_NULL,
    null=True,
    blank=True,
    related_name='contact_profile',
    verbose_name='Пользователь'
)
```

**Как это работает**:
- **Сотрудники**: У них есть `User` (для авторизации) и `Contact` (для данных сотрудника)
  - Связь: `Contact.user` → `User`
  - Обратная связь: `User.contact_profile` → `Contact`
- **Внешние пользователи**: У них есть только `User`, без `Contact`
  - `User.contact_profile` = `None`
  - Используются данные из `User` (username, email)

**Преимущества**:
- ✅ Гибкость: поддерживает и сотрудников, и внешних пользователей
- ✅ Минимум изменений: только одно поле в Contact
- ✅ Обратная совместимость: существующие Contact не затронуты
- ✅ Простая логика: легко проверить наличие Contact

#### 6.1.2. Отображение пользователей в чате

**Логика получения данных пользователя**:

```python
def get_user_display_name(user):
    """
    Возвращает отображаемое имя пользователя.
    Для сотрудников - из Contact.full_name,
    для внешних - из User.get_full_name() или username.
    """
    if hasattr(user, 'contact_profile') and user.contact_profile:
        return user.contact_profile.full_name
    return user.get_full_name() or user.username

def get_user_avatar(user):
    """
    Возвращает аватар пользователя.
    Для сотрудников - из Contact.avatar,
    для внешних - None или дефолтный аватар.
    """
    if hasattr(user, 'contact_profile') and user.contact_profile:
        return user.contact_profile.get_cropped_avatar_url()
    return None  # или URL дефолтного аватара
```

#### 6.1.3. Список пользователей для чата

**API endpoint для получения списка пользователей**:

- **Все активные пользователи** (включая внешних):
  ```python
  User.objects.filter(is_active=True)
  ```
  
- **Только сотрудники** (с Contact):
  ```python
  User.objects.filter(contact_profile__isnull=False, is_active=True)
  ```

**Настройка**: Выбор зависит от требований - нужны ли внешние пользователи в списке для создания чата.

#### 6.1.4. Использование в чате

## 10. Управление файлами и автоудаление

### 10.1. Стратегия временного хранения

#### 10.1.1. Принцип работы
- Файлы хранятся на сервере временно (по умолчанию 30-90 дней)
- После истечения срока файлы автоматически удаляются
- В базе данных остается запись о файле (метаданные), но сам файл удаляется
- Пользователи могут скачать файл только пока он не удален

#### 10.1.2. Реализация автоудаления

##### Вариант 1: Django Management Command (Простой)
```python
# messaging/management/commands/cleanup_old_files.py
# Запускается по cron раз в день
python manage.py cleanup_old_files
```

##### Вариант 2: Celery Periodic Task (Рекомендуется)
- Автоматическое выполнение задачи по расписанию
- Более гибкое управление
- Можно настроить через Django Admin

#### 10.1.3. Настройка периода хранения
- Настройка в `settings.py`: `MESSAGING_FILE_RETENTION_DAYS = 30`
- Или через админку (если создать модель Settings)
- По умолчанию: 30 дней для обычных файлов, 90 дней для важных (опционально)

#### 10.1.4. Обработка удаленных файлов
- При попытке скачать удаленный файл - показывать сообщение "Файл больше не доступен"
- В интерфейсе можно показывать иконку "файл удален" вместо превью
- Опционально: уведомление пользователям перед удалением (за 7 дней до удаления)

### 10.2. Альтернативные решения

#### 10.2.1. Внешнее хранилище (для будущего)
- Yandex Object Storage (S3-совместимое)
- AWS S3
- MinIO (self-hosted S3)
- **Преимущества**: Неограниченное хранилище, файлы не занимают место на сервере
- **Недостатки**: Требует настройки, возможны расходы

#### 10.2.2. Мониторинг использования диска
- Регулярная проверка размера папки с файлами
- Уведомления администратору при превышении лимита
- Автоматическое сокращение периода хранения при нехватке места
